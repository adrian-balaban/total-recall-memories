# SQL
This page describes the SQL language supported in Flink, including Data Definition Language (DDL), Data Manipulation Language (DML) and Query Language. Flink's SQL support is based on Apache Calcite which implements the SQL standard.
This page lists all the supported statements supported in Flink SQL for now:
- SELECT (Queries)
- CREATE TABLE, CATALOG, DATABASE, VIEW, FUNCTION
- DROP TABLE, DATABASE, VIEW, FUNCTION
- ALTER TABLE, DATABASE, FUNCTION
- ANALYZE TABLE
- INSERT
- UPDATE
- DELETE
- DESCRIBE
- EXPLAIN
- USE
- SHOW
- LOAD
- UNLOAD

## Data Types
Please see the dedicated page about data types.
Generic types and (nested) composite types (e.g., POJOs, tuples, rows, Scala case classes) can be fields of a row as well.
Fields of composite types with arbitrary nesting can be accessed with value access functions.
Generic types are treated as a black box and can be passed on or processed by user-defined functions.
For DDLs, we support full data types defined in page Data Types.
Notes: Some of the data types are not supported in SQL queries yet (i.e. in cast expressions or literals). E.g. STRING, BYTES, RAW, TIME(p) WITHOUT TIME ZONE, TIME(p) WITH LOCAL TIME ZONE, TIMESTAMP(p) WITHOUT TIME ZONE, TIMESTAMP(p) WITH LOCAL TIME ZONE, ARRAY, MULTISET, ROW.

# Data Types
Flink SQL has a rich set of native data types available to users.

## Data Type
A data type describes the logical type of a value in the table ecosystem. It can be used to declare input and/or output types of operations.
Flink's data types are similar to the SQL standard's data type terminology but also contain information about the nullability of a value for efficient handling of scalar expressions.
Examples of data types are: INT; INT NOT NULL; INTERVAL DAY TO SECOND(3); ROW<myField ARRAY<BOOLEAN>, myOtherField TIMESTAMP(3)>.
A list of all pre-defined data types can be found below.

### Data Types in the Table API
Java/Scala: Users of the JVM-based API work with instances of org.apache.flink.table.types.DataType within the Table API or when defining connectors, catalogs, or user-defined functions. A DataType instance has two responsibilities: (1) Declaration of a logical type which does not imply a concrete physical representation for transmission or storage but defines the boundaries between JVM-based/Python languages and the table ecosystem. (2) Optional: Giving hints about the physical representation of data to the planner which is useful at the edges to other APIs. For JVM-based languages, all pre-defined data types are available in org.apache.flink.table.api.DataTypes.
Python: Users of the Python API work with instances of pyflink.table.types.DataType within the Python Table API or when defining Python user-defined functions. A DataType instance has responsibility: Declaration of a logical type which does not imply a concrete physical representation for transmission or storage but defines the boundaries between Python languages and the table ecosystem. For Python, those types are available in pyflink.table.types.DataTypes.
Java: recommended star import: `[code: import static org.apache.flink.table.api.DataTypes.*; ... (95 chars)]`
Scala: `[code: import org.apache.flink.table.api.DataTypes._ ... (91 chars)]`
Python: `[code: from pyflink.table.types import DataTypes ... (103 chars)]`

#### Data Type and Python Type Mapping
For Python user-defined functions, the inputs will be converted to Python objects corresponding to the data type and the type of the user-defined function result must also match the defined data type. For vectorized Python UDFs, the input types and output type are pandas.Series. The element type of the pandas.Series corresponds to the specified data type. [table: 21 rows]

#### Physical Hints
Physical hints are required at the edges of the table ecosystem where the SQL-based type system ends and programming-specific data types are required. Hints indicate the data format that an implementation expects. For example, a data source could express that it produces values for logical TIMESTAMPs using a java.sql.Timestamp class instead of using java.time.LocalDateTime which would be the default. With this information, the runtime is able to convert the produced class into its internal data format. In return, a data sink can declare the data format it consumes from the runtime.
Java: `[code: // tell the runtime to not produce or consume java.time.LocalDateTime ... (354 chars)]`
Scala: `[code: // tell the runtime to not produce or consume java.time.LocalDateTime ... (373 chars)]`
Attention: physical hints are usually only required if the API is extended. Users of predefined sources/sinks/functions do not need to define such hints. Hints within a table program (e.g. field.cast(TIMESTAMP(3).bridgedTo(Timestamp.class))) are ignored.

### Date and Time
#### DATE — date year-month-day, 0000-01-01 to 9999-12-31. Compared to SQL standard, range starts at year 0000. SQL `DATE`; Java/Scala `DataTypes.DATE()`; Bridging [table: 5 rows]; Python `DataTypes.DATE()`.
#### TIME — time without time zone, hour:minute:second[.fractional], up to nanosecond precision, 00:00:00.000000000 to 23:59:59.999999999. Leap seconds not supported (semantics closer to java.time.LocalTime). A time with time zone is not provided. SQL `[code: TIME ... (12 chars)]`; Java/Scala `DataTypes.TIME(p)`; Bridging [table: 7 rows]; Python `DataTypes.TIME(p)`. Attention: precision in DataTypes.TIME(p) must be 0 currently. Declared using TIME(p), p = digits of fractional seconds 0..9, default 0.
#### TIMESTAMP — timestamp without time zone, year-month-day hour:minute:second[.fractional], up to nanosecond precision, 0000-01-01 00:00:00.000000000 to 9999-12-31 23:59:59.999999999. Leap seconds not supported (semantics closer to java.time.LocalDateTime). A conversion from and to BIGINT is not supported as this would imply a time zone; this type is time zone free. For more java.time.Instant-like semantics use TIMESTAMP_LTZ. SQL `[code: TIMESTAMP ... (82 chars)]`; Java/Scala `DataTypes.TIMESTAMP(p)`; Bridging [table: 4 rows]; Python `DataTypes.TIMESTAMP(p)`. Attention: precision in DataTypes.TIMESTAMP(p) must be 3 currently. Declared using TIMESTAMP(p), p = digits of fractional seconds 0..9, default 6. TIMESTAMP(p) WITHOUT TIME ZONE is a synonym.
#### TIMESTAMP WITH TIME ZONE — timestamp with time zone, year-month-day hour:minute:second[.fractional] zone, up to nanosecond precision, 0000-01-01 00:00:00.000000000 +14:59 to 9999-12-31 23:59:59.999999999 -14:59. Leap seconds not supported (semantics closer to java.time.OffsetDateTime). Compared to TIMESTAMP_LTZ, the time zone offset information is physically stored in every datum; used individually for every computation, visualization, or communication to external systems. SQL `[code: TIMESTAMP WITH TIME ZONE ... (52 chars)]`; Java/Scala `DataTypes.TIMESTAMP_WITH_TIME_ZONE(p)`; Bridging [table: 3 rows]; Python not supported. Declared using TIMESTAMP(p) WITH TIME ZONE, p = digits of fractional seconds 0..9, default 6.
#### TIMESTAMP_LTZ — timestamp with local time zone. Leap seconds not supported. Compared to TIMESTAMP WITH TIME ZONE, the time zone offset information is not stored physically in every datum. Instead, the type assumes java.time.Instant semantics in UTC time zone at the edges of the table ecosystem. Every datum is interpreted in the local time zone configured in the current session for computation and visualization. This type fills the gap between time zone free and time zone mandatory timestamp types by allowing the interpretation of UTC timestamps according to the configured session time zone. SQL `[code: TIMESTAMP_LTZ ... (96 chars)]`; Java/Scala `DataTypes.TIMESTAMP_LTZ(p)`; Bridging [table: 8 rows]; Python `DataTypes.TIMESTAMP_LTZ(p)`. Attention: precision in DataTypes.TIMESTAMP_LTZ(p) must be 3 currently. Declared using TIMESTAMP_LTZ(p), p = digits of fractional seconds 0..9, default 6. TIMESTAMP(p) WITH LOCAL TIME ZONE is a synonym.

An interval of year-month consists of +years-months with values -9999-11 to +9999-11. Value representation same for all resolutions (e.g. interval of months of 50 = +04-02). ### Constructured Data Types
#### ARRAY — array of elements with same subtype. Compared to SQL standard, max cardinality cannot be specified but is fixed at 2,147,483,647; any valid type supported as subtype. SQL `ARRAY<t>`; Java/Scala `DataTypes.ARRAY(t)`; Bridging [table: 5 rows]; Python `DataTypes.ARRAY(t)`. Declared using ARRAY<t>. t ARRAY is a synonym (INT ARRAY == ARRAY<INT>).
#### MAP — associative array mapping keys (including NULL) to values (including NULL). Cannot contain duplicate keys; each key maps to at most one value. No restriction of element types; user ensures uniqueness. Extension to SQL standard. SQL `MAP<kt, vt>`; Java/Scala `DataTypes.MAP(kt, vt)`; Bridging [table: 4 rows]; Python `DataTypes.MAP(kt, vt)`.
#### MULTISET — multiset (bag). Allows multiple instances for each element with a common subtype. Each unique value (including NULL) is mapped to some multiplicity. No restriction of element types. SQL `MULTISET<t>`; Java/Scala `DataTypes.MULTISET(t)`; Bridging [table: 4 rows]; Python `DataTypes.MULTISET(t)`. t MULTISET is a synonym (INT MULTISET == MULTISET<INT>).
#### ROW — sequence of fields. A field consists of a field name, field type, and an optional description. The most specific type of a row of a table is a row type. Compared to SQL standard, an optional field description simplifies handling with complex structures. A row type is similar to the STRUCT type. SQL `[code: ROW<n0 t0, n1 t1, ...> ... (112 chars)]`; Java/Scala `[code: DataTypes.ROW(DataTypes.FIELD(n0, t0), ...) ... (145 chars)]`; Bridging [table: 3 rows]; Python `[code: DataTypes.ROW([DataTypes.FIELD(...)]) ... (149 chars)]`. Declared using ROW<n0 t0 'd0', n1 t1 'd1', ...>. ROW(...) is a synonym.

### User-Defined Data Types
#### STRUCTURED — user-defined object. Compared to ROW, structured types are distinguishable even if they contain the same set of fields (e.g. Visit(amount DOUBLE) is distinct from Interaction(amount DOUBLE) due to its identifier). Identified by a class name and contain zero, one or more attributes. A type cannot be defined so that one of its attribute types (transitively) refers to itself. Internally converted into suitable data structures; serialization and equality checks managed by the system based on the logical type.
SQL: `[code: STRUCTURED<'c', n0 t0, n1 t1, ...> ... (74 chars)]`. Declared using STRUCTURED<'c', n0 t0 'd0', n1 t1 'd1', ...> where c is the class name.
Java/Scala: Usually defined inline and can be reflectively extracted from a corresponding implementation class (e.g. in the signature of an eval() method). They enable reusing existing JVM classes without manually defining the schema. If the class name matches a class in the classpath, the system will convert a structured object to a JVM object at the edges of the table ecosystem. The implementation class must provide either a zero-argument constructor or a full constructor that assigns all attributes. The class name does not need to be resolvable in the classpath — it may be used solely to distinguish between objects with identical attribute sets. In Table API and UDF calls, the system will attempt to resolve the class name to an actual implementation class; if resolution fails, Row is used as a fallback.
Inline structured types can be created from regular POJOs if the implementation class meets requirements: (1) class must be globally accessible (declared public, static, not abstract); (2) must offer a default constructor with zero arguments or a full constructor that assigns all fields; (3) all fields must be readable (public declaration or getter following getField()/isField()/field()); (4) all fields must be writable (public declaration, fully assigning constructor, or setter following setField(...)/field(...)); (5) all fields must be mapped to a data type either implicitly via reflective extraction or explicitly using @DataTypeHint annotations; (6) fields declared static or transient are ignored. Reflective extraction supports arbitrary nesting as long as a field type does not (transitively) refer to itself. The declared field class must be contained in the list of supported JVM bridging classes. For some classes an annotation is required (e.g. @DataTypeHint("DECIMAL(10, 2)") for java.math.BigDecimal).
Python: not supported.

(469 chars)]`; or explicit extraction `[code: DataTypes.of(Class); ... (67 chars)]`. Bridging to JVM Types [table: 4 rows].

### Other Data Types
#### BOOLEAN — boolean with (possibly) three-valued logic of TRUE, FALSE, and UNKNOWN. SQL `BOOLEAN`; Java/Scala `DataTypes.BOOLEAN()`; Bridging [table: 3 rows]; Python `DataTypes.BOOLEAN()`.
#### DESCRIPTOR — describes an arbitrary, unvalidated list of columns. Return type of calls to DESCRIPTOR(`c0`, `c1`). Intended to be used in arguments of process table functions (PTFs). The runtime does not support this type; it is a pure helper type during translation and planning. Table columns cannot be declared with this type. Functions cannot declare return types of this type. SQL `DESCRIPTOR`; Java/Scala `DataTypes.DESCRIPTOR()`; Bridging [table: 2 rows].
#### VARIANT — semi-structured data. Supports storing any semi-structured data, including ARRAY, MAP (with keys of type STRING), and scalar types. The data type of the fields are stored in the data structure, close to the semantics of JSON. Compared to ROW and STRUCTURED, VARIANT has the flexibility to support highly nested and evolving schema. Allows deeply nested data structures (arrays within arrays, maps within maps, or combinations). Allows schema evolution — storage of data with changing or unknown schemas without requiring upfront schema definition. SQL `VARIANT`. Variant type is usually produced by the PARSE_JSON function: `[code: SELECT PARSE_JSON('{"a":1,"b":["a","b","c"]}') AS v ... (51 chars)]`. Java/Scala `DataTypes.VARIANT()`; Bridging [table: 2 rows].
#### BITMAP — bitmap data that stores 32-bit integers in a compressed form using RoaringBitmap. Useful for efficiently representing and querying large sets of integers. Supports a variety of built-in scalar functions and aggregate functions. Extension to SQL standard. SQL `BITMAP`. ## Casting
Flink Table API and SQL can perform casting between a defined input type and target type. Some casting operations can always succeed regardless of the input value, others can fail at runtime (i.e. where there is no way to create a value for the target type). E.g. always possible to convert INT to STRING, but cannot always convert STRING to INT. During the planning stage, the query validator rejects queries for invalid type pairs with a ValidationException, e.g. when trying to cast a TIMESTAMP to an INTERVAL. Valid type pairs that can fail at runtime will be accepted by the query validator, but requires the user to correctly handle failures.
Casting can be performed using one of two built-in functions:
- CAST: the regular cast function defined by the SQL standard. It can fail the job if the cast operation is fallible and the provided input is not valid. The type inference will preserve the nullability of the input type.
- TRY_CAST: an extension to the regular cast function which returns NULL in case the cast operation fails. Its return type is always nullable.
Example: `[code: CAST('42' AS INT) --- returns 42 of type INT NOT NULL ... (422 chars)]`.

### Legacy casting
Pre Flink 1.15 casting behaviour can be enabled by setting table.exec.legacy-cast-behaviour to enabled. In Flink 1.15 this flag is disabled by default. In particular, this will: disable trimming/padding for casting to CHAR/VARCHAR/BINARY/VARBINARY; CAST never fails but returns NULL, behaving as TRY_CAST but without inferring the correct type; formatting of some casting to CHAR/VARCHAR/STRING produces slightly different results. We discourage the use of this flag and strongly suggest for new projects to keep this flag disabled and use the new casting behaviour. This flag will be removed in the next Flink versions.
