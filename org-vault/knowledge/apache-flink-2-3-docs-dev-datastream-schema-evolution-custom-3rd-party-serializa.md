# State Schema Evolution

Flink streaming apps run long/indefinitely; data schemas evolve with the app. This page covers evolving state type's data schema (restrictions vary by type and state structure: ValueState, ListState, etc). Relevant ONLY if using state serializers generated by Flink's own type serialization framework (i.e. state descriptor not configured with specific TypeSerializer/TypeInformation — Flink infers). Whether schema can be evolved depends on the serializer used to read/write persisted bytes; handled transparently by Flink-generated serializers. For custom TypeSerializer implementing schema evolution, see Custom State Serialization.

## Evolving state schema
Steps: take a savepoint; update state types in application (e.g. modify Avro type schema); restore job from savepoint — on first state access Flink assesses whether schema changed and migrates if necessary. Migration automatic, independent per state: Flink checks if new serializer has different schema than previous; if so, previous serializer reads state to objects, written back with new serializer.

## Supported data types for schema evolution
Currently schema evolution supported ONLY for POJO and Avro types. Recommended to use Pojo or Avro for state data types. Plans to extend (FLINK-10896).

### POJO types
Rules: fields can be removed (previous value dropped in future checkpoints/savepoints); new fields can be added (initialized to default value for type per Java); declared field types cannot change; POJO class name cannot change (incl. namespace). Same rules apply to Java records (POJO types since 1.19). POJO state schema can only be evolved when restoring from a savepoint with Flink newer than 1.8.0; with versions older than 1.8.0 schema cannot change.

### Avro types
Fully supported, as long as schema change compatible per Avro's schema resolution rules. Limitation: Avro generated classes used as state type cannot be relocated or have different namespaces on restore.

## Schema Migration Limitations
To ensure correctness. Workarounds: custom serializer or state processor api.

### Schema evolution of keys is not supported
Key structure cannot be migrated (non-deterministic behavior). E.g. POJO key with dropped field → multiple separate keys become identical; Flink can't merge values. RocksDB relies on binary object identity, not hashCode — any change to keys' object structure → non-deterministic behavior.

### Kryo cannot be used for schema evolution
No way for framework to verify incompatible changes. If a data-structure containing a type is serialized via Kryo, that contained type cannot undergo schema evolution. E.g. POJO containing List<SomeOtherPojo> — List and contents serialized via Kryo → no schema evolution for SomeOtherPojo.

# Custom Serialization for Managed State

Guideline for users requiring custom serialization for state: how to provide a custom state serializer + best practices for implementing serializers that allow schema evolution. Irrelevant if using Flink's own serializers.

## Using custom state serializers
When registering managed operator/keyed state, StateDescriptor specifies state name and type info. Can bypass and let Flink use your own custom serializer by instantiating StateDescriptor directly with your TypeSerializer implementation.

## State serializers and schema evolution
On restore from savepoints, Flink allows changing serializers used to read/write previously registered state (not locked into specific schema). New serializer registered for state may have different schema than previous. Besides read/write logic, consider how serialization schema can change. Schema (data model OR serialized binary format) changes for: data schema of state type evolved (add/remove field from POJO); serialization format upgraded after data schema change; serializer config changed. To detect schema change on restore, a snapshot of the state serializer written along with state bytes — abstracted as TypeSerializerSnapshot.

### The TypeSerializerSnapshot abstraction
Point-in-time info = single source of truth about state serializer's write schema + info mandatory to restore an identical serializer. writeSnapshot/readSnapshot define what's written/read. Snapshots are versioned (getCurrentVersion); readSnapshot receives the version. resolveSchemaCompatibility detects schema change at restore — returns TypeSerializerSchemaCompatibility:
- compatibleAsIs(): new serializer compatible (identical schema); may be reconfigured in resolveSchemaCompatibility.
- compatibleAfterMigration(): different schema, can migrate — previous serializer (recognizes old schema) reads bytes to objects, rewritten with new serializer.
- incompatible(): different schema, cannot migrate.
TypeSerializerSnapshot also serves as factory to restore previous serializer — restoreSerializer() instantiates serializer recognizing previous schema/config to safely read previous data.

### How Flink interacts with TypeSerializer and TypeSerializerSnapshot
Orthogonal to serializer/snapshot implementation.

#### Off-heap state backends (e.g. EmbeddedRocksDBStateBackend)
Register new state with serializer schema A → serializer reads/writes on every access, state written in schema A → take savepoint → snapshot extracted via TypeSerializer#snapshotConfiguration, written to savepoint with serialized state bytes (schema A) → restore re-accesses with new serializer schema B → previous snapshot restored → state bytes NOT deserialized on restore, loaded back to backend (still schema A) → resolveSchemaCompatibility checks → if changed & migration possible: previous serializer (from restoreSerializer()) deserializes bytes to objects, re-written with new serializer (schema B); all entries of accessed state migrated all-together before processing continues → if incompatible: state access fails with exception.

#### Heap state backends (e.g. HashMapStateBackend)
Register with schema A → serializer maintained by backend → take savepoint serializing all state with schema A → snapshot extracted, written → state objects serialized to savepoint (schema A) → on restore: deserialize state into objects in heap — previous serializer (schema A) from restoreSerializer() deserializes bytes to objects; all state already deserialized → re-access with new serializer schema B → resolveSchemaCompatibility → if migration required nothing happens (state already deserialized) → if incompatible fails → next savepoint serializes all state with schema B.

## Predefined convenient TypeSerializerSnapshot classes
SimpleTypeSerializerSnapshot and CompositeTypeSerializerSnapshot. Must always have own independent subclass implementation (don't share snapshot classes across serializers).

### SimpleTypeSerializerSnapshot
For serializers with no state/config — serialization schema solely defined by serializer class. Only 2 compatibility results: compatibleAsIs() (same class) or incompatible() (different class). Example: IntSerializer (no state/config, format defined by class, only read by another IntSerializer). Base super constructor expects a Supplier of serializer instances (used for restore serializer + type checks). Example IntSerializerSnapshot.

### CompositeTypeSerializerSnapshot
For serializers relying on multiple nested serializers ("outer" serializer — e.g. MapSerializer key/value, ListSerializer, GenericArraySerializer). Outer snapshot contains nested snapshots → nested compatibility checked independently; final result considers all nested. Deals with reading/writing nested snapshots + resolving final compatibility. Must implement: getCurrentOuterSnapshotVersion() (version of outer snapshot binary format); getNestedSerializers(TypeSerializer); createOuterSerializerWithNestedSerializers(TypeSerializer[]). Example MapSerializerSnapshot. If outer snapshot has additional static config (e.g. GenericArraySerializer element class), also implement: writeOuterSnapshot(DataOutputView); readOuterSnapshot(int,DataInputView,ClassLoader); resolveOuterSchemaCompatibility(TypeSerializerSnapshot). Default empty implementations if no outer info. Example GenericArraySerializerSnapshot: outer snapshot version must be upticked when outer snapshot serialization format changes; avoid Java serialization by writing classname + dynamic loading on read.

## Implementation notes and best practices
1. Flink restores serializer snapshots by instantiating with classname — snapshot is entry point to reading state in savepoints. To avoid classname changes/instantiation failures: avoid anonymous/nested classes; have public nullary constructor.
2. Avoid sharing same TypeSerializerSnapshot class across different serializers — complicates resolveSchemaCompatibility/restoreSerializer; bad separation of concerns.
3. Avoid Java serialization for serializer snapshot content — write class name, dynamically load on read. Java serialization of a type class → snapshot may be unreadable once class implementation changed (no longer binary compatible).

## Migrating from deprecated serializer snapshot APIs before Flink 1.7
Pre-1.7: TypeSerializerConfigSnapshot (deprecated, will be removed, replaced by TypeSerializerSnapshot); compatibility checks lived in TypeSerializer#ensureCompatibility(TypeSerializerConfigSnapshot). Old TypeSerializerConfigSnapshot couldn't instantiate previous serializer → serializer instance written to savepoints via Java serialization (undesirable — susceptible to class availability/Java serialization readability; limited to same serializer). Migrate: implement new TypeSerializerSnapshot subclass; return it in snapshotConfiguration(); restore from pre-1.7 savepoint and take new savepoint (old TypeSerializerConfigSnapshot must still be in classpath, ensureCompatibility not removed); once savepoint taken with Flink 1.7 contains TypeSerializerSnapshot and no serializer instance → safe to remove old abstractions.

## Migrating from deprecated TypeSerializerSnapshot#resolveSchemaCompatibility(TypeSerializer newSerializer) before Flink 1.19
Pre-1.19: old serializer (maybe in Flink library) had to meet future need, or old serializer's resolveSchemaCompatibility(TypeSerializer newSerializer) modified; no way to specify compatibility with old serializer in new serializer → schema evolution unsupported in some scenarios. Since 1.19 direction reversed: old method removed, replace with resolveSchemaCompatibility(TypeSerializerSnapshot oldSerializerSnapshot). Steps: implement new method (same logic); remove old method.

# 3rd Party Serializers

Custom type not serializable by Flink type serializer → Flink falls back to Kryo. Register your own serializer or a serialization system (Google Protobuf, Apache Thrift) with Kryo via pipeline.serialization-config (type class + serializer), or programmatically via Configuration. Custom serializer must extend Kryo's Serializer class (done for Protobuf/Thrift already). Include Maven dependencies (Apache Thrift / Google Protobuf). Adjust versions as needed.

### Issue with using Kryo's JavaSerializer
Registering Kryo's JavaSerializer for custom type may cause ClassNotFoundExceptions even though class is in user code jar — known issue, Kryo's JavaSerializer may use wrong classloader. Use org.apache.flink.api.java.typeutils.runtime.kryo.JavaSerializer instead (reimplemented, uses user code classloader). See FLINK-6025.

# User-Defined Functions

Most operations require a UDF. Ways to specify:
- Implementing an interface (MapFunction<String,Integer>).
- Anonymous classes (new MapFunction<...>(){...}).
- Java 8 Lambdas (data.filter(s -> s.startsWith("http://")); data.reduce((i1,i2) -> i1+i2)).
- Rich functions: transformations can take a rich function instead (RichMapFunction instead of MapFunction) — anonymous class also possible.

## Accumulators & Counters
Simple constructs with add operation and final accumulated result available after job ended. Counter: increment via Accumulator.add(V). At job end Flink sums (merges) partial results, sends to client. Useful for debugging/quick data insights. Built-in accumulators (implement Accumulator interface): IntCounter, LongCounter, DoubleCounter; Histogram (discrete bins, map Integer→Integer; e.g. words-per-line distribution). Usage: create accumulator object in transformation function (private IntCounter numLines = new IntCounter()); register in open() of rich function with name (getRuntimeContext().addAccumulator("num-lines", this.numLines)); use anywhere in operator incl open()/close() (this.numLines.add(1)); result in JobExecutionResult from execute() (myJobExecutionResult.getAccumulatorResult("num-lines")) — only works if execution waits for completion. All accumulators share single namespace per job — same accumulator in different operator functions merged by name. Custom accumulators: implement Accumulator interface. Accumulator<V,R> most flexible (V=value to add, R=final result; e.g. histogram V=number, R=histogram); SimpleAccumulator for cases where both types same (e.g. counters).
